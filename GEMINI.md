# Gemini CLI Project Instructions - Social Care Interoperability Standards

This document serves as the foundational engineering instructions and context for any LLM agent or developer working in the **Social Care Interoperability Standards** repository.

---

## 1. Project Overview

The **Social Care Interoperability Standards** website (deployed at [standard.socialcaredata.io](https://standard.socialcaredata.io)) is an open-source knowledge base and specifications portal. Developed in partnership by **Social Finance**, **the Open Data Institute (ODI)**, and **Coram**, it documents interoperability standards and schemas for social care data exchange (including children's social care placements, adult social care, and multi-agency information sharing for safeguarding and wellbeing).

### Main Technologies
*   **Static Site Generator:** Jekyll (Ruby)
*   **Templating Language:** Liquid and Kramdown (Markdown with extension support)
*   **Client-side Search:** Pagefind (integrated at build time)
*   **Data Modeling:** LinkML (LinkML YAML schemas are the single source of truth for standard properties)
*   **Semantic Web / Ontologies:** RDF/Turtle (`.ttl`) and SHACL (`shacl-shape.ttl`) for semantic model encoding and validation
*   **Tooling & Validation Platforms:** Custom Node.js packages for JSON-LD validation and LinkML-to-Markdown-table rendering.
*   **Containerization:** Docker & Docker Compose for consistent cross-platform builds and live-reloads.

## 3. Core Development Workflows & Commands

### A. Local Development (Docker-based)
To spin up a live-reloading Jekyll development server with page-regeneration enabled:
```bash
docker compose up
```
*   **Web Portal URL:** View the site locally at `http://localhost:4000` (or `http://127.0.0.1:4000` on WSL2/Windows).
*   **Live-Reload Tweaks:** If file updates are not trigger-building, update `docker-compose.yml` to specify the `--force_polling` argument on `jekyll serve`.
*   **Windows Gemfile lock issue:** If you encounter `Gemfile.lock is locked to x64-mingw`, run:
    ```bash
    docker compose run --rm socialcaredata-jekyll bundle lock --add-platform x86_64-linux
    ```

### B. Building & Link Checking
The site utilizes strict link validation hooks that run after Jekyll compiles the files into `dist/`. If any link validator fails, the build exits with code `1`. To compile the site locally and run link validation:
```bash
docker compose run --rm build
```
This runs three post-write validation scripts in `src/_plugins`:
1.  **Internal Link Validator (`check_internal_links.rb`):** Checks for broken relative paths inside the generated `dist/` folder and flags any internal links written as absolute URLs (which should be relative).
2.  **Insecure Link Validator (`check_insecure_links.rb`):** Rejects any external links using insecure `http://` protocols, requiring `https://` everywhere.
3.  **External Link Validator (`check_external_links.rb`):** Tests external URLs with HEAD/GET requests to verify they are active. *Note: Skipped in local watch mode to keep regeneration speeds fast, but active on full builds and CI.*

### C. Data Modeling (LinkML Source of Truth)
The definitive specification of the Children's Social Care Placements data standard is **`src/assets/model/placements/placements-standard.yaml`**. 
> ⚠️ **CRITICAL RULE:** **NEVER edit OWL/RDF Turtle (`.ttl`) or SHACL (`-shape.ttl`) files directly!** 
> You must edit the authoritative LinkML YAML schema instead, then regenerate the downstream artifacts.

To regenerate the downstream artifacts, you need Python $\ge 3.11$ with `linkml` installed:
```bash
# Install LinkML tooling
pip install linkml

# Generate SHACL shapes (output matches src/assets/shacl/shacl-shape.ttl)
gen-shacl --non-closed --suffix Shape placements-standard.yaml > placements-standard-shape.ttl

# Generate OWL / RDF Turtle representation
gen-owl --consolidate-cardinality-axioms --skip-vacuous-min-zero-cardinality-axioms --skip-vacuous-local-range-axioms placements-standard.yaml > placements-standard.ttl
```

### D. JSON-LD Schema Validation
To validate sample JSON-LD instances (under `src/assets/shacl/examples`) against the SHACL constraints in `src/assets/shacl/shacl-shape.ttl`:
```bash
cd src/assets/shacl/validation
npm install
npm run validate
```
This uses [`rdf-validate-shacl`](https://www.npmjs.com/package/rdf-validate-shacl) to run compliance tests. A zero (`0`) exit code is returned if all files prefixed with `valid-*.jsonld` conform to the shape, and all files prefixed with `invalid-*.jsonld` fail validations.

### E. Node.js `schema-table` Custom Module
The `src/assets/js/schema-table` directory is a standalone Node.js package that extracts classes and properties from LinkML models to render tables in Kramdown format.
*   **Class tables:** Generated for a LinkML class entity describing its slots, types, cardinalities, descriptions, and linked taxonomies.
*   **Vocabulary tables:** Collapsible tables representing SKOS taxonomic permissible values under an enum.
*   **Diff tables:** Renders interactive colored HTML diff comparisons (additions highlighted in green, deletions in red/strikeout) between two versions of a schema file using the `--previous <file>` option.
*   **Testing:** Run unit tests for this module natively:
    ```bash
    cd src/assets/js/schema-table
    npm install
    npm test
    ```

## 4. Engineering Standards & Coding Conventions

### Spacing & Spacing Configurations (`.editorconfig`)
Ensure your IDE matches the project's formatting profile:
*   **Indentation:** 4 spaces (except Markdown `.md` files which use 2 spaces).
*   **Encoding:** UTF-8.
*   **Line Endings:** LF only.
*   **Whitespace:** Auto-trim trailing whitespace, ensure a single blank trailing newline at the end of every file.

### Content Front Matter Specifications
All Markdown pages (under `src/_pages/`) must specify structured Front Matter according to their layouts. Typical publication metadata fields include:
*   `layout`: `publication`, `use-case`, `default`, `post`, etc.
*   `reference`: Unique standard identifier (e.g., `PUB00`, `PUB01`, `UC01`).
*   `status`: Allowed lifecycle states are `draft`, `proposed`, `effective`, `obsolete`.
*   `version`: Version string matching the standard (e.g., `00`, `01`, `02`).
*   `data_model`: Points to the authoritative LinkML YAML definition file.
*   `breadcrumbs`: Categories array for the breadcrumb navigation.

### Liquid Custom Tags Usage
Do not hardcode property/vocabulary tables or differences. Use the following custom Liquid tags embedded directly in your Markdown page content:

1.  **Schema Table (`{% schema_table %}`):**
    ```liquid
    {% schema_table page.data_model PlacementAvailability %}
    ```
    *Args: `[schema_file_path] [entity_or_enum_or_property_name]`*
2.  **Schema Table Difference (`{% schema_table_diff %}`):**
    ```liquid
    {% schema_table_diff current_model_path previous_model_path PlacementAvailability %}
    ```
    *Args: `[current_schema_path] [previous_schema_path] [entity_or_enum_or_property_name]`*

## 5. Continuous Integration (CI) and Deployment (CD)

Both workflows run on Github Actions on every PR and main merge respectively:
1.  **CI Validation Pipeline (`ci.yml`):** Automatically provisions an Ubuntu runner, sets up Node.js and Ruby environments, installs global `pagefind` search tool, restores the cached bundle of gems, installs the `schema-table` node dependencies, and executes `bundle exec jekyll build`. This automatically verifies the integrity of internal, insecure, and external links before code can be merged.
2.  **Continuous Deployment (`cd.yml`):** Performs the same compilation steps as the CI pipeline, uploads the final compiled static site directory (`dist/`) to GitHub Pages artifacts, and deploys it automatically to standard.socialcaredata.io.
